# Design

## Context

See `proposal.md` and the nine delta specs. The reviewed source is at `1cf85ac`: the controller runs one Tokio task per start, probes before sequential/segmented transfer, and uses `OutputSession`, `FileCheckpointStore`, and a pathname-based publication step. `RedirectTracker` currently compares unnormalized Location text using response headers; `FileSink::open` uses `create(true), truncate(false)` for both fresh and resumed output. `PendingAdmission::finalize` compares validators only when both sides provide them. Sequential checkpoint saves lack the data sync present in segmented saves. The release gate accepts passing non-approving evidence before checking its age/commit. Tests already have loopback HTTP, crash/restart, sink fault, and platform fixtures; prior change-local specs and `docs/acceptance-v1.md` state stronger guarantees than these paths deliver. There are no main OpenSpec specs yet.

## Goals / Non-Goals

**Goals:** Share security/verification decisions between transfer modes; make pre-publication byte coverage and artifact identity explicit; fail closed when inputs cannot justify reuse, durable progress, or release approval. Preserve the existing typed success/error API and no-clobber publication contract where possible.

**Non-Goals:** Defend against a caller deliberately supplying a malicious transport/store or a host attacker who controls the engine process; promise atomic, hostile-writer-resistant replacement on unsupported filesystems; claim total RSS is bounded by the transfer ledger; claim a production release from planning or targeted loopback tests.

## Decisions

1. **Resolve and scope redirect requests at the transport boundary.** Replace string-splitting origin comparisons with URL resolution and normalized scheme/host/effective-port comparison before constructing the next request; loop detection and downgrade use resolved targets too. Make the hop policy depend on the *outgoing request* credential context, never response headers. Classify `Authorization`, `Cookie`, `Proxy-Authorization`, configured provider output, and explicitly scoped custom credential headers; latch a cross-origin strip across subsequent hops, including a return to the original host, unless the caller explicitly opts into cross-origin forwarding. Never attach proxy auth to origin requests. Construct one sanitized/authenticated request context after probe that sequential and segmented workers both use; challenge retries remain bounded and origin-scoped. Prefer this to adjusting only the `RedirectTracker` test or adding `authorization` to worker headers: either alone leaves one path leaking or unauthenticated. Cover HEAD, GET, H1/H2, relative/absolute and multiple hops with two dummy-credential listeners.

2. **Use owned output plus accepted-byte coverage, not filesystem size.** For a fresh job, allocate a unique, unpredictable same-directory temporary name with exclusive/no-follow creation and reject reuse of existing `.part` contents; adapt `TempFileSpec`, `OutputSession::create/reopen`, and sidecar naming so the checkpoint identifies the actual owned file. Track accepted, fully written intervals in the sequential and segmented coordinator (seed only from securely admitted checkpoint ranges). Before commit, require exact `[0,total)` coverage for known lengths and normal EOF plus a truncate-to-acknowledged-offset for unknown lengths. Keep caller digests and file length checks as additional verification, never coverage substitutes. Shared completion logic runs after worker drain and before `publish`. Unlike a simple truncate-on-open fix, this also detects preallocation holes, sparse files and resumptions with misleading lengths. Retest short known bodies and stale tails with real adapters, abort/retry and preallocation.

3. **Bind checkpoint state and publication to a verified file.** On disk, move to a versioned checkpoint describing an owned temp name, file identity and a digest of the admitted covered bytes (or bounded per-range digests), as well as remote validators. Verify these on admission before taking the fully-complete fast path, and re-check the opened regular file's identity at publication. A saved/current pair needs matching strong ETag or eligible Last-Modified; a missing former validator, weak-only tag or mere size match cannot authorize reuse. Apply existing resource-change failure semantics when a validator *differs*; where evidence is simply insufficient or legacy state lacks binding, discard the old checkpoint safely and start fresh, or fail closed if safe cleanup is impossible. A complete checkpoint can skip GET only after that admission. Avoid trusting `metadata(path)` which follows symlinks. On platforms with directory-relative/descriptor-bound no-follow primitives use them; otherwise require a trusted destination/checkpoint directory that excludes non-cooperating concurrent writers, check file identity under the existing cooperative lease and fail closed when ownership cannot be established. An attacker with write access to the directory can replace any pathname between checks on some platforms, so never advertise unconditional hostile-directory protection; document the trust precondition and test symlink, hardlink, replacement and lockfile/sidecar paths with unrelated scratch files. Retain atomic no-replace/replace semantics for a securely owned source. Prefer this to trusting random names or `symlink_metadata` alone, which cannot eliminate an entry-swap race.

4. **Unify mode-aware checkpoint persistence and bound its size.** Move sequential cadence/pause and segmented saves through one routine: in Durable mode settle acknowledged writes, `sync_data` the output, then serialize/save checkpoint and sync sidecar/directory; only after successful save advance persisted range state. Performance mode keeps page-cache acknowledgement. Checkpoint serialization reservation uses checked, conservative JSON upper bounds for every field (including escaped validators), or a bounded streaming encoder; cap enforcement is before allocation and before calling an injected store. Charge and release actual retained bytes to job and controller ledgers. Prefer this to increasing fixed estimate padding: remotely supplied validators can exceed any constant. Ordered sync/save/pause/crash fault tests cover both transfer modes.

5. **Centralize job lifetime controls.** Add controller-wide RAII permits around actual admitted jobs; because `start` is synchronous and returns a handle/join pair, use immediate typed admission failure when the cap is exhausted rather than spawning an unbounded waiting queue. Release permits even on abort. Take one monotonic deadline at admission and pass the same cancellation/deadline context to probe, admission, retries, headers, body reads, worker waits and chunked hashing. Replace plain retry sleeps and blocked HTTP waits with cancellation/deadline-aware selects, and check the deadline before beginning publication. The atomic publication step is a commit boundary: if the rename/link succeeded, report completion (with any post-commit warning), not a misleading timeout. Prefer this to separate per-worker timeouts, which drift and can allow one path to outrun the advertised job limit. Document the admission rejection and terminal outcome without silently changing `start`'s signature.

6. **Make diagnostics and counters terminal-safe.** Count network payload bytes once in `wire_amplification`; use unique completed output bytes as the denominator, including safely reused bytes (a resumed job may therefore have a ratio below 1). Keep the benchmark's server-emitted-byte metric separately labeled. Give each job an independent terminal signal beside the broadcast hub; `EventStream::next` drains queued events, then returns `None` after completion even if the handle still retains its hub, and lagged listeners can inspect the final snapshot. Default diagnostic URL rendering masks userinfo and *all query values* (including unfamiliar secret keys), with optional explicit caller masking retained; never change the URL sent on the wire. A new checkpoint representation avoids storing raw original/final URLs when current request/probe and an opaque job identity suffice; ensure default sidecar/temp files are private to the owning user and document custom-store trust requirements. Prefer keeping raw URLs only in memory to relying on a small list of secret-key names or default directory permissions.

7. **Fail closed at the release boundary and preserve auditability.** In `release_gate.py`, validate status, date, future-time, commit and equivalence for every required passing fragment before categorizing it as approving vs non-approving; require an explicit candidate commit for production verdicts. Extend self-tests for stale/wrong-commit non-approving evidence, absent commit and reviewed exceptions. Reconcile `docs/acceptance-v1.md` claims with reproduced counterexamples, replace the missing `KDownSpec.md` rustdoc reference, enable and evaluate member workspace lints, extend API signature checks with an external consumer fixture, and attach exact-commit Linux/macOS/Windows, fuzz/dynamic/dependency/crash, controlled WAN/loopback and RSS observations. Keep `docs/performance-report-v1.md` honest about noisy loopback and non-RSS memory accounting. No gate reports stable while high-severity defects or required evidence remain unresolved; old/historical manifest fragments are not silently relabeled for a new candidate. Prefer this to fixing only the smoke early-return because `commit=None` independently bypasses revision binding.

## Risks / Trade-offs

- [New checkpoint format and owned temp filenames discard old resume progress] → Version the format, document loss of old partial reuse, safely clean or quarantine under the destination lease, and test legacy migration; never reinterpret old ranges as trusted.
- [Descriptor-bound publication is not uniformly portable and hostile directory writers can race path operations] → Use platform-specific secure primitives where available and otherwise enforce/document a trusted-directory precondition; fail rather than claim a security guarantee that pathname checks cannot provide.
- [Admitted-range digests and data sync add CPU/I/O, particularly for large resumes] → Use bounded chunked verification, record throughput/RSS on matched baselines, and keep Performance mode's documented weaker durability without weakening identity/coverage verification.
- [A deadline during filesystem commit or slow hashing can produce surprising terminal timing] → Check between bounded chunks and before commit, keep atomic publication non-interruptible and truthfully report post-commit success; test boundary races.
- [Existing test fixtures assume fixed `.part` paths or event streams never close] → Update fixtures and migration notes alongside behavior; test consumer-visible signatures and stop conditions before release.
- [Checkpoint secrets may be retained in backups or custom stores outside engine control] → Do not store raw URL text in new default sidecars, use restricted permissions, and document caller/custom-store storage responsibility.

## Migration Plan

1. Land P0 isolated end-to-end regression fixtures and fixes for redirect scope, owned temporary output, coverage and checkpoint validator/binding; keep release blocked and version the checkpoint and partial-file format together. A failed secure migration causes a conservative clean restart or structured failure, never trust old partial bytes.
2. Add common durability save, auth context, deadline/cancellation and job admission; update config/API docs and mode-parity/fault/restart tests. Maintain compatible public facade types where possible; record intentional changes to resume and event behavior.
3. Correct accounting and URL/storage privacy, wire terminal stream semantics and member lint/API checks; run targeted and full locked suites on supported platforms and update acceptance docs.
4. Repair the evidence gate and rerun mandatory candidate-bound verification on appropriate hosts/runners. Only declare stable if all required evidence actually passes for the exact revision; rollback to the prior released version keeps its earlier documented behavior but does not restore a production-stability claim.
