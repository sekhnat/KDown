# Spec Delta

## Purpose

Makes runtime-control events describe applied worker concurrency and rate-limit updates accurately so consumers can react without mistaking one control for another.

## ADDED Requirements

### Requirement: Concurrency events reflect applied manual control
A successful manual concurrency update on a segmented job SHALL publish one `ConcurrencyChanged { workers: u64 }` event describing the applied, bounded desired worker count after the update is visible. It SHALL NOT publish `RateLimitChanged` as a consequence of a concurrency-only update. Calls that cannot apply the update, including a handle with no segmented job, SHALL NOT publish a false concurrency event. Existing worker control behavior, including bounds and manual override, SHALL be preserved.

#### Scenario: Update within bounds
- **WHEN** a subscriber observes a running segmented job and calls `set_concurrency(6)` within its configured bounds
- **THEN** the desired worker count becomes 6, exactly one concurrency-change event reports `workers: 6`, and no rate-limit-change event is generated by that call

#### Scenario: Clamped update
- **WHEN** manual concurrency is requested outside the job's configured worker bounds
- **THEN** the event reports the applied clamped count, not the requested out-of-range value

#### Scenario: No segmented job
- **WHEN** a handle has not acquired a segmented job and `set_concurrency` is called
- **THEN** no event claims that worker concurrency changed

### Requirement: Rate-limit events reflect rate changes
A rate-limit-only update SHALL continue to publish `RateLimitChanged` with the effective bytes-per-second value, using `None` for unlimited, after the rate change is applied; it SHALL NOT synthesize `ConcurrencyChanged`.

#### Scenario: Live rate update
- **WHEN** a subscriber calls `set_rate_limit` with a positive value and subsequently with zero
- **THEN** the corresponding rate-limit events report that value and then unlimited, without a concurrency-change event caused by those calls
