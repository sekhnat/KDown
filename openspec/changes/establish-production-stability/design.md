# Design

## Context

See `proposal.md` and the five delta specs for behavior. `DownloadController::run` currently returns `Result<DownloadResult, DownloadError>` but terminal transfer failures can be `Ok(DownloadResult { status: Failed, error: Some(_) })`; `start` adds a Tokio join layer. `lib.rs` publicly exports implementation modules, and existing integration tests and README HTTP/checkpoint injection examples import them directly. `EngineConfig::buffer_pool_max_bytes` bounds a pool unused by the transfer path; `read_buffer_size` is not a Hyper socket limit. Shared writer byte caps already exist for the optional pipeline. `EngineMetrics::snapshot` exports counters but no budget peaks. The three-OS PR matrix, parser fuzz targets/corpus smoke, scheduler property tests, and loopback-only benchmark smoke provide starting points; `docs/benchmark-profiling.md` explicitly excludes Hyper buffering from the current memory claim. Workspace MSRV is 1.85 and version is 0.1.0.

## Goals / Non-Goals

**Goals:** Make the stable-to-consumers contract auditable; meter every retained payload/metadata stage against job and engine caps without counting shared `Bytes` twice; make a release decision from reproducible evidence rather than CI green alone.

**Non-Goals:** Bound whole-process RSS (allocator/runtime overhead and kernel socket memory are separate); promise bandwidth or latency on arbitrary public networks; make internal adapters a supported extension API by accident; preserve source compatibility with the current 0.1 surface. Do not claim production stability until all release gates actually run and pass.

## Decisions

1. **Terminal API and classification.** Introduce a `CompletedDownload` value with non-optional final path and accounting, plus `DownloadRunError` with typed `Transfer(TransferFailure)`, `Infrastructure(EngineFailure)`, and `Cancelled(CancellationSummary)` branches, all carrying available redacted diagnostic/partial metadata. Both `run` and spawned job return `Result<CompletedDownload, DownloadRunError>`; Tokio's `JoinError` remains a distinct outer await failure for `start`. Network/protocol/integrity/retry exhaustion classify as transfer failures; filesystem, checkpoint persistence, internal admission/engine faults classify as infrastructure; user cancellation is distinct. Map each existing terminal construction and record metrics exactly once on all branches. Check commit/verification before constructing success. Prefer this over `Ok(enum Completed|Failed|Cancelled)` because `is_ok()` must never report a failed download. Map existing `DownloadError` categories internally before retiring ambiguous exported status/error fields.

2. **Public API inventory before visibility changes.** Produce a whitelist from external quickstart, supported config/metrics/event/error types and required signature dependencies. Mark `scheduler`, `job`, `io`, `resume`, `fuzz_targets` internal and facade-reexport only deliberately supported types. HTTP transport construction stays public; explicitly retire the currently advertised README-scripted `HttpExecution`/`ScriptedHttp` external seam in the breaking migration guide, keeping adapters internal for conformance tests. Move integration tests that need internal state-machine access to crate-internal unit/property modules; external tests exercise facade behavior. Audit indirect public references before hiding modules, and add an external consumer compile/negative visibility check plus API baseline policy. Alternative of retaining all `pub mod`s with documentation-only disclaimers fails the requested narrow surface. Publish semver policy for post-cleanup versions, `#[non_exhaustive]` where expansion is intended, and MSRV policy.

3. **Single accounted byte budget, not a repurposed pool field.** Add validated `EngineConfig` transfer-memory limits: per-job and controller-wide aggregate caps with component maxima for network/client ingress, held/queued frames, writer-held bytes, and checkpoint data; keep pool budget explicitly separate or deprecate it. Give each live allocation an ownership-tagged reservation; move the tag with zero-copy `Bytes` into a writer without charging twice, and release on drop/ack/failure/cancel. Writer queue admission shares the aggregate ledger; reserve before holding a frame and before allocating checkpoint serialization/interval state, with a bounded range-count/serialized-size policy. Bound headers/response metadata and HTTP/1 read buffers; configure HTTP/2 connection windows, streams and read buffering so their maximum reserved connection footprint is known and accounted before establishing connections. Use bounded socket/HTTP ingress rather than merely pausing reads *after* Hyper has buffered an unbounded frame. Validate the transport version/configuration with oversized-frame and slow-consumer tests plus independent RSS profiling; if Hyper cannot provide a provable bound for some mode, disable/restrict that mode or change transport rather than declaring success. Adopt fair, cancellation-aware admission and typed insufficient-budget refusal for an atomic allocation larger than a limit, avoiding waiting while holding a resource needed to free capacity. Existing per-writer cap becomes subordinate to the single aggregate ledger. Alternative of counting only application-held chunks repeats the documented gap.

4. **Metrics and scope.** Add per-job and engine-wide budget snapshots with `limit_bytes`, `current_bytes`, and `high_water_bytes`, both total and component breakdown, exact scopes (job/controller) and lifetime semantics (job through terminal outcome; controller since creation/reset). Track current/peak when reservations change, not by sampling RSS; display pre-reserved client capacity explicitly rather than reporting an unknown actual value as zero. Include these in terminal diagnostics/bench records. Keep actual process RSS as an auxiliary measured axis, not the promised bound. Use saturation-safe accounting and test cancellation/panics/abort without leaked reservations.

5. **Fault and platform matrix.** Extend `crates/engine/tests/support/test_server.rs`, `http/scripted.rs`, the existing sink fault seam, and platform filesystem tests to drive deterministic seeds/profiles: fixed and random latency/jitter, loss, bandwidth, resets, redirected CDN/cache validators, proxy auth/CONNECT, incorrect or ignored Range, slow/full/short-write storage, pause/resume/restart and many jobs. Require exact bytes/hash on published output, no publication on failure, sound checkpoint reuse and resource peaks within caps; record failing seeds as regression fixtures. Run platform-specific rename/no-replace, locks/sharing, path normalization, sparse/preallocation, and crash/restart tests in the existing matrix. Use emulated CDN/proxy fixtures as blocking tests; optional live interop probes are supporting evidence, not nondeterministic PR gates.

6. **Layered verification.** Add locked dependency/vulnerability audit to PR (with reviewed advisory exceptions), retain cross-OS build/test/clippy/MSRV and deterministic property/corpus tests, and run short fuzz/state-machine checks where runner support is dependable. Scheduled and release jobs run real per-target fuzz budgets, longer randomized scheduler/checkpoint/commit and multi-job stress with seed capture, and targeted Miri on isolated state-machine tests plus sanitizer/thread/concurrency checks on suitable nightly Linux runners. Unsupported configurations have documented equivalent or keep release blocked; never silently mark a skipped check successful. Retain logs/toolchain versions and a release checklist with actionable vulnerability and severity triage. Alternative of putting all long-running workloads on every PR is costly/noisy and was rejected.

7. **Reproducible performance budgets.** Extend `crates/engine/benches/throughput.rs` and `scripts/bench_check.sh` with machine-readable per-axis output and controlled network emulation profiles: loopback; low-latency (10 ms RTT, 1 ms jitter, 100 Mbps, 0.1% loss); WAN (80 ms RTT, 20 ms jitter, 20 Mbps, 1% loss). Include H1/H2 and job/worker scale points (1/4/16 jobs and 1/4/8 workers where supported), disk profile and fixed input/hash, warmup, >=5 repetitions, medians and spread. Compare only on matched hosts/configs or an explicit calibrated baseline; initial threshold policy: throughput and concurrency scaling no more than 10% below approved baseline, CPU/byte no more than 15% above, amplification no more than 0.05 above baseline, and measured managed-memory high-water never over its configured cap (also track <=10% baseline drift for unchanged caps). Baselines are reviewed/versioned after representative runs, never silently rewritten by CI. Current loopback-only `bench_check.sh --smoke` remains a PR scenario check; scheduled/release comparison plus current correctness/security/stress evidence gates a production release. If measurement noise exceeds a threshold, rerun on controlled hardware and record the disposition rather than weaken the gate silently.

## Risks / Trade-offs

- [Hyper buffers or H2 multiplexing exceed a controllable reservation] → Establish worst-case window/stream/header limits and test adversarial frames before claiming the bound; restrict unsupported modes or change client if proof fails.
- [Narrowing visibility breaks internal integration tests or advertised scripted seams] → Inventory and relocate tests, document explicit removal and replacement examples, verify downstream consumer compilation and increment version according to compatibility policy.
- [Cross-platform fault injection and WAN emulation vary by runner] → Pin toolchain/fixture configs, isolate hardware-sensitive gates on dedicated matching runners, preserve seeds and publish unsupported-case evidence; never substitute green smoke for release gates.
- [Baselines become stale or machine load distorts comparisons] → Record host/config/protocol signatures, profile version and noise, rerun matched measurements, require reviewed baseline updates.
- [Security advisories or sanitizer availability blocks release] → Triage applicability with recorded reviewed exceptions or equivalent checks; do not auto-ignore missing evidence.

## Migration Plan

1. Record existing external API imports and baseline metrics; provide a 0.1-to-new-surface migration table before removal. Rollback of a release means reverting to the last published 0.1 version, not silently restoring ambiguous `Ok(Failed)` behavior under the new API.
2. Implement typed outcomes and update internal/error metrics and examples; then restrict facade/module visibility and relocate internal-only tests, verifying downstream examples as an external crate.
3. Establish budget envelope/proof for HTTP modes, integrate writer/checkpoint/client reservations and snapshots, then update the formerly pool-only memory claim only after adversarial tests pass.
4. Add deterministic adverse-condition/platform fixtures, PR/scheduled CI and versioned benchmarks; record quantitative baselines and release evidence. Do not mark production-stable while a required gate is failing or unmeasured.
