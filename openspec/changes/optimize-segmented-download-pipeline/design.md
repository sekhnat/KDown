# Design

## Context

See `proposal.md` for motivation and `specs/{transfer-core,resume-and-storage,observability}/spec.md` for behavior. Today `OutputSession::share_write_handles` lends workers an `Arc<tokio::Mutex<FileSink>>`; `FileSink::write_at` seeks then writes, and `transfer_lease` invokes `FlushLevel::PageCache` for each body chunk. Worker loops save `CheckpointStore::save_atomic` synchronously, use independent timers and read progress fields with separate Relaxed loads. The scheduler leases up to `max_segment_size` despite `initial_segment_size`; idle workers sleep 20 ms; workers above a reduced desired count eventually exit. `BufferPool` is constructed per worker but unused by the Hyper `Bytes` path, and `try_acquire` currently always returns a buffer or waits. The benchmark's `retransferred_bytes` is populated from `warnings.len()`. No installed main specs exist, although past changes use these capability names.

Existing seams to preserve: `OutputSession` controls partial-file disposition, fault injection and exclusive reclaim; `CheckpointStore` can be injected and the sidecar atomically renames checkpoint metadata; `SegmentScheduler` owns inclusive interval coverage and generation checks; `SingleStreamController` owns final checksum/size verification, output publication and cleanup. Current `DurabilityMode::Performance` promises OS-acknowledged writes, not power-loss safety, while `Durable` promises synchronized data before checkpoint metadata.

## Goals / Non-Goals

**Goals:** Maintain an exclusive output owner while allowing parallel offset writes; make successful write acknowledgment, reconciled progress, data sync and persisted checkpoint distinct; preserve retry and lifecycle ordering with a small body path; obtain comparable performance evidence before tuning adaptive defaults.

**Non-Goals:** Redesign single-stream transfer or checkpoint file format, change connection-pool/H2 connection count policy, promise an absolute process-RSS cap for Hyper's internal buffers, or add io_uring, IOCP-specific engines, unsafe seqlocks, custom allocators, new hashing, HTTP/3 or speculative platform machinery.

## Decisions

### 1. Output authority, positional writes and blocking I/O

Keep `OutputSession` as the sole lifecycle owner of the temp file and final publication/abort authority. Lend workers cloneable write-only capabilities over a shared immutable file handle; the owner keeps a separate synchronization capability and cannot reclaim/close/publish until every writer and its in-flight write has terminated. The existing `Sink` trait and `FileSink` sequential path can remain for nonsegmented use; do not retain a mutex-protected seek/write as a hidden fallback for segmented transfers. A safe standard-library platform adapter uses `std::os::unix::fs::FileExt::write_at` on Unix and `std::os::windows::fs::FileExt::seek_write` on Windows (with a cfg-scoped wrapper); a partial-write loop advances the checked `u64` offset, retries interruption and rejects `Ok(0)`. Report structured storage errors and preserve scripted output faults at the capability boundary. Handle `Bytes` by reference/clone, not a copy into `BytesMut`.

Avoid blocking Tokio networking threads on disk by using a bounded, long-lived blocking writer lane per active worker (one `spawn_blocking` task per lane, not per chunk). A worker submits an owned `Bytes` and offset, awaits the acknowledgment before publishing progress or reading another chunk; writer lanes can write concurrently to the same file because each operation is positional. A one-item queue/acknowledgment prevents unbounded retained chunks. Shut down and join lanes before reclaim. Sync/checkpoint persistence run in a separate blocking coordinator task or `spawn_blocking` per infrequent checkpoint; neither serializes ordinary writes. Alternative direct synchronous writes on Tokio are simpler but can starve network tasks; `tokio::fs` seek/write still hides shared-cursor synchronization; one blocking spawn per chunk costs scheduling overhead. Benchmark the lane overhead and optimize only with evidence.

### 2. Durability and checkpoint authority

Use separate notions of (a) worker-local successfully written interval, (b) scheduler-validated candidate coverage, (c) successful data-sync eligible coverage in durable mode, and (d) last successfully persisted checkpoint coverage/revision. Scheduler `completed` currently means *written* (despite naming it durable); update terminology/trackers so retries and completion can use written coverage without claiming a durability guarantee. A single job-level checkpoint coordinator wakes on the configured interval, pause boundary and terminal/keep-partial settlement. It snapshots coherent cells and reconciles them under the scheduler lock, captures immutable candidate ranges and a revision, then releases the lock before filesystem operations. Snapshot never includes data whose write acknowledgment has not returned. Once progress is sampled, durable mode syncs the temp file (`sync_all` initially, matching existing durable `FlushLevel::FsyncFile`; profile `sync_data` only if metadata semantics permit), then calls the existing atomic checkpoint store. Performance mode saves after write acknowledgment without a file sync; `PageCache` flush per chunk is removed. The sidecar still syncs its temporary checkpoint and parent directory in durable mode. A sync occurring while later writes continue is safe: the snapshot's acknowledged writes precede invocation of sync; later writes are not included in that snapshot. A failed sync never triggers a save of its snapshot. On failed save, do not advance the in-memory persisted revision; after a post-rename directory-sync error the on-disk file may already contain the newer *safe* ranges, so restart validates whichever atomic checkpoint is visible rather than assuming the old file was restored.

Do not advance or persist a checkpoint on a failed or stale generation. At lease boundaries, reconcile written progress before fail/release/complete and preserve tail-only retry. Serialize snapshot capture with generation invalidation; any generation rollover must fence coordinator saves so an old snapshot cannot be persisted *after* invalidation (stop/join pending coordinator work before resetting/restarting, or recheck epoch under a save gate). Checkpoint coalescing compares candidate intervals plus relevant identity/validator metadata against the last saved revision, not merely a chunk counter. Pause/keep-partial waits for the coordinator's save result before reporting resumability; on cancellation delete/keep-file modes, join/disable coordinator before controller cleanup; on successful completion, join all writers/coordinator, reclaim ownership, verify, finalize and atomically publish, then delete checkpoint. Reuse `CheckpointStore` rather than bypassing injected implementations. Alternative per-worker save plus a sync lock is harder to order and still duplicates work. Current single-stream checkpoint behavior remains outside this change except shared helper corrections needed for durability guarantees.

### 3. Coherent progress and terminal error

For each worker use a single-writer cell with atomic sequence, lease id, generation, lease start and written-through. Writer stores odd sequence, then fields, then even sequence; readers retry if the two sequence reads differ or are odd. **Use `SeqCst` for every field and sequence access in the first safe implementation**: a single global order prevents a reader from treating mixed publications as one record, even across reset/reuse; write acknowledgment happens-before publication via the worker's task continuation. Avoid a merely `Release` sequence around Relaxed payload atomics without a formal ordering proof. The writer must be unique to a cell; reader validates lease id/generation and bounds with scheduler before accepting progress. Handle sequence wrap conservatively (u64 practically unreachable, or reset only when no readers). Add concurrent stress and, if feasible, Loom for the isolated primitive; profile `SeqCst` cost before weakening orderings. An alternative `Mutex<ProgressRecord>` is safer/simple but adds hot-path lock acquisition; a packed atomic cannot encode full u64 fields.

A separate atomic fatal flag gives a cheap `Acquire` check. Installing a terminal failure takes a small mutex protecting the authoritative error; installer locks, sets error if absent, then `store(true, Release)` and wakes parked workers. If another failure races, it cannot replace the first recorded error. Never publish the flag before the error object; controller joins workers/coordinator before taking the error. Cancellation and generation invalidation remain distinct terminal controls.

### 4. Runtime rate and metric shards

Use a stable per-job `Arc<TokenBucket>` from job startup, interpreting rate zero as unlimited; `TokenBucket::acquire` already checks an atomic rate before its internal state lock. `set_rate_limit` updates the bucket's rate in place rather than swapping an `Option<Arc<_>>` through the job's outer mutex; preserve handle getter semantics and coordinate pre-start updates so the same bucket reaches the eventual job. Updates affect subsequent acquires, not chunks already granted. Worker-local network/completed/retry/wasted accounting uses `worker(worker_idx)` rather than slot zero; track unique completed bytes only after scheduler acceptance/settlement (never count re-read bytes as unique), and count wire bytes when received even if later writes fail. Do not cache-pad metric shards unless profiles show false sharing. The existing `DownloadResult` exposes network bytes but not unique completed/wasted byte counts; use snapshots for benchmark records or add documented nonbreaking fields/accessors as needed.

### 5. Scheduler, wakeups and persistent pool

Extend `SchedulerPolicy` with target segment size and split threshold. With today's non-optional `initial_segment_size` treat it as explicit (default 8 MiB): preserve its current documented value while fixing its ignored behavior. Introduce a separate opt-in automatic sizing selector (or an `Option`/enum with backward-compatible migration) for `ceil(remaining / (initial_active_workers * oversubscription))`, clamped to min/max; start with factor 3 and tune from benchmarks. Compute remaining from validated intervals, not total length. Add direct scheduler queries (`active_count`, pending flag, largest splittable lease, `is_finished`) instead of allocating `active_leases()` vectors in idle checks. Moving split threshold to policy removes worker's hard-coded 256 KiB.

Create up to `max_workers` persistent tasks; each only acquires a lease while its index is below desired (or via activation permits). Reductions settle the current lease before parking; never cancel an in-flight write and claim its unwritten remainder, and never drop writer lanes until job teardown. In fixed mode start at configured `max_workers` (or equal min/max); explicitly adaptive mode starts at `min_workers`. Clamp manual updates to configured `[min_workers, max_workers]` and document priority: a manual `set_concurrency` pins the desired count and suspends auto-adjustment for the remainder of the job, avoiding competing controllers. A `watch` revision/state signal (or equivalent persistent versioned notification) is preferable to bare `Notify` for multiple parked readers. Read current revision/state, register changed/notification before deciding to sleep, then recheck state; publish revision after state transition while holding relevant scheduler serialization. Notify on requeue, new work, split eligibility/progress, desired-worker changes, resume, fatal, cancellation and completion. Paused body handling also uses cancellation/resume notifications instead of a 20 ms loop. The state predicate, not the notification, determines whether to work; deterministic race tests cover registration-before/after updates. Alternative fixed sleeps waste wakeups; semaphore-only gates need a separate wake for requeue and shutdown.

### 6. Adaptive controller, memory and allocation

Adaptive mode is opt-in so existing fixed jobs do not silently change defaults. Evaluate useful unique completed-byte delta per stable window, also sampling received bytes, wasted/retransferred bytes, retries/429/503, worker idle ratio and positional-write latency. Start at min, probe +1, compare smoothed useful goodput against baseline with a material-gain hysteresis band, revert or reduce on sustained pressure, and require cooldown after any change. Put tunable thresholds/windows behind internal constants/config only once representative benchmarks justify values; never use raw wire throughput as the primary objective. HTTP/2 range streams may multiplex a single connection; leave `H2ConnectionPolicy` unchanged.

Remove the unused per-worker `BufferPool` construction from `worker_loop`; do not copy Hyper `Bytes` into a pool. Existing `buffer_pool_max_bytes` cannot be advertised as a bound on Hyper's own buffers: it bounds *explicitly retained/staged transfer bytes* if used. Keep one owned frame pending per active worker; if profiling shows a meaningful queue/backpressure need, add a **job-shared byte permit** for queued payload with exact length accounting and bounded one-item lanes, splitting oversized `Bytes` by cheap views rather than copying. Expose/document that ingress frames or Hyper internal buffering may transiently exceed this explicit staging budget; do not silently instantiate one full-budget pool per worker. If `BufferPool` remains public for other callers, `try_acquire()` returns `None` when exhausted, `acquire()` waits without blocking an async executor, and total allocation respects configured bytes (including too-small-budget validation).

Keep `set_len` for portable logical sizing. Optional physical reservation is a later gated adapter: on Linux use supported fallocate-style APIs only where portable bindings already exist or a justified dependency is approved; on other Unix/Windows use a safe supported facility only after proof/benchmark, otherwise fall back. Unsupported operation/filesystem or unsupported flags fall back; ENOSPC, permission, and other real errors surface. No fallback may silently replace a previously valid temp file. This optimization is not a correctness dependency.

### 7. Evidence and verification

Repair benchmark accounting (`ResourceRecord.retransferred_bytes = warnings.len()` is invalid) and test arithmetic from synthetic snapshots: elapsed, new unique bytes, network bytes, retry overhead. Preserve small in-process smoke fixtures, add parameterized 32 MiB/256 MiB/1 GiB × H1/H2 × 1/2/4/8; run larger and 16 workers manually. Avoid fixture-server `Vec` copying/whole-file allocation in authoritative comparisons: launch a process-isolated fixture server, verify fixture hash and client result, record client-only CPU and RSS, connection count and pressure. Compare pre-change baseline and each major milestone on matching hardware, protocol, filesystem (tmpfs/NVMe/disk), checkpoint mode and rate shaping. Document commands for Linux `perf stat`/`pidstat`/`strace`/RSS and portable fallbacks; attribute syscall count, context switches, CPU cycles/instructions per useful byte, worker idle %, writes/checkpoint/sync latency. Add controlled server variants (ignore ranges, per-connection/aggregate throttles, 429/503, reset, validator changes) and optional `tc netem` RTT/loss/bandwidth for manual runs. No universal throughput gate; ensure no output-mutex serialization, redundant checkpoint or per-chunk flush, no worse correctness, and document material CPU/memory regressions.

## Risks / Trade-offs

- [Blocking writer lanes consume threads and cloned handles] → Cap by `max_workers`, bound payload queues, compare CPU/context switches with baseline; reuse worker lanes until termination.
- [Partial writes, high offsets and fault hooks bypass existing sink behavior] → Checked offset loop, fault-injected short/error results and cross-platform tests; keep lifecycle in `OutputSession`.
- [Durable sync overlaps new writes or metadata save fails after rename] → Freeze immutable candidate snapshot before sync; never include subsequent progress in that save; validate checkpoint on restart and distinguish save success from visibility.
- [Coordinator holds stale generation or races cleanup] → Gate generation change with coordinator lifecycle, join coordinator before cleanup/publication and stress cancellation/validator changes.
- [High memory from Hyper ingress outside explicit staging control] → Describe budget scope honestly, bound queued payloads and benchmark peak RSS; add job-wide permits only if necessary.
- [Adaptive controller oscillates or harms servers] → Opt-in, conservative +1 probing, pressure signals/hysteresis and stable-window/cooldown tests; manual override wins.
- [Physical allocation unsupported or changes failure timing] → Keep portable `set_len`, treat unsupported as fallback, propagate real ENOSPC and permission failures, keep feature optional.

## Migration Plan

Implement and benchmark in the proposed 12 milestones: metric baseline; positional output; durability ordering; checkpoint ownership; progress/controls; scheduler sizing; notifications; persistent pool; opt-in adaptive controller; memory cleanup; optional physical allocation; final comparisons. Keep existing fixed concurrency/default durability/H2 connection policy and temp/sidecar formats. Document new opt-in adaptive/automatic-size settings and `set_concurrency` clamp/manual-override behavior; no silent format migration. Validate Unix and Windows compilation/tests (including publish/cleanup paths) before release. Roll back optional adaptive, auto-size or physical allocation independently if regressions occur; keep the positional-write and checkpoint ordering correctness fixes, or revert the whole change with its tests rather than restoring an unsafe mixed output/checkpoint implementation.
