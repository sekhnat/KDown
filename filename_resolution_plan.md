# Automatic Filename Resolution — repository-aligned specification

## Goal and scope

Callers may opt into downloading to an **existing directory** instead of naming an output file. After the current metadata probe, KDown derives a safe, immutable filename from the final HEAD response and/or URLs, then acquires destination ownership, admits resume state, transfers and publishes. Existing explicit-file calls (with existing policies) retain their API, ordering and observable event sequence. `OverwritePolicy::Rename` is a new opt-in policy supported for **both** file and directory targets.

This document is a specification for a **future implementation**. This review changes only this markdown file; code, tests, API inventories and OpenSpec artifacts mentioned below are implementation deliverables, not work in the current review.

The HTTP probe is HEAD plus the existing optional validating `GET bytes=0-0`; neither response body is consumed by the probe. The name is fixed from the HEAD `ProbeMetadata` (not intermediate redirects or a later transfer response). If the validating GET redirects separately, it does not rename the job. For directory mode, the pre-network lease/checkpoint-admission guarantees in §14.6/§15.5 are explicitly relaxed; for explicit files, including `Rename`, destination selection/admission stays before networking.

## Source-compatible public API

`DownloadRequest` is a public, exhaustively constructible struct with a public `destination: PathBuf` field. **Do not remove or add fields**, change `DownloadRequest::new`, or change the signatures of `DownloadController::{run,start,run_with_handle}`: either change breaks external struct literals or method references. Do not add a field to the similarly public `EngineConfig` merely for naming options.

Add a separate opt-in `DirectoryDownloadRequest::new(url, directory)` type wrapping an ordinary `DownloadRequest` plus private directory options. Expose `request_mut()` so callers can set existing headers, integrity, overwrite and resume policies. Add `with_fallback_filename(...)` and `with_max_filename_bytes(...)` builders. Defaults: fallback `download`, maximum final basename **250 UTF-8 bytes** (255 minus the current `.part` sibling suffix). Validate options and directory existence/type before networking with the existing `Configuration` category: fallback must already be a nonempty, unchanged-by-sanitization single normal component; byte cap must be at most 250 and at least the fallback's byte length (and at least 7 for `Rename`, reserving one stem byte plus ` (999)`). The directory is caller-selected, not server-selected; it must already exist, and the existing trusted-directory assumption applies (no guarantee against another actor replacing its entries).

Add symmetric controller entry points `start_to_directory`, `run_to_directory`, `run_to_directory_with_handle` that delegate to a shared private runner; do not introduce a parallel transfer implementation. Internally keep the mode and options separate until resolution, then pass the chosen destination through the existing request-dependent transfer/cleanup paths. Public file requests continue to mean an explicit filename, even when their path happens to be a directory.

Add `DownloadHandle::resolved_destination() -> Option<&Path>` backed by a shared `OnceLock<PathBuf>`: for existing explicit-file policies, the known input file path may be available immediately; for `Rename` and directory mode, publish only the leased final choice. Add `Event::DestinationResolved { path: String }` for directory requests and file requests using `Rename`, emitted once, after selection and lease acquisition, before meaningful transfer progress. No new event in existing explicit-file modes. `CompletedDownload.final_path` and `Event::Committed` retain their current meaning. A lagged broadcast subscriber may miss the new event, so the handle accessor is the reliable live lookup after resolution.

## Resolution precedence

For directory requests, try, in order:

1. Final HEAD `Content-Disposition` `filename*` (valid UTF-8 RFC 5987/8187 ext-value).
2. Final HEAD `Content-Disposition` `filename` (quoted-string with quoted-pair unescaping, or token).
3. Final segment of the final redirected HEAD URL path, if nonempty.
4. Final segment of the original URL path, if nonempty.
5. Caller-configured fallback name (default `download`).

A trailing `/` yields no URL basename; it does **not** take the previous segment. Parse URLs with the existing URI representation so query and fragment are not part of the basename; percent-decode the selected URL segment exactly once before sanitization. Malformed percent escapes skip that URL candidate; well-formed escapes producing invalid UTF-8 decode lossily. A decoded `%2F`/`%5C` is rejected as specified below, so it cannot change directories. Empty, malformed or unresolvable sources are skipped; the validated fallback always resolves. Only the first surviving candidate wins. No transfer-time `Content-Disposition` may change it.

Implement a parser that preserves **both** parameter candidates through sanitization (e.g. add a plain fallback hint to internal `ProbeMetadata` or store ordered hints): the current single `filename_hint: Option<String>` alone loses `filename` when a syntactically valid `filename*` sanitizes to nothing. Preserve the existing `filename_hint` use in tests as appropriate; `http::probe` is an internal seam, not a public API. Use the first `Content-Disposition` header only, as `probe::interpret` already does. Neither the HTTP parser nor transport should log header values. To honor raw non-UTF-8 `filename` support, the HEAD header extraction in `http::transport` must decode **that header only** with `String::from_utf8_lossy` instead of the current `to_str().unwrap_or("")`; do not globally change unrelated header interpretation.

`filename*` must be `UTF-8'language'value` (language may be empty); reject unsupported charsets, malformed percent escapes or invalid decoded UTF-8, then try `filename`. Quoted `filename` respects semicolons inside quotes and quoted-pair escapes; malformed parameters are skipped without failing the download. Duplicate same-name parameters use their first well-formed occurrence. Disposition type (`attachment`, `inline`, etc.) is advisory, but garbage with no valid parameters supplies no hint. Bound parser work by the existing HTTP header limits; never allow panics or unbounded parsing for hostile values.

## Sanitization and path construction

Extend `io::sanitize_filename` instead of creating a separate sanitizer. Keep the existing public/internal wrapper behavior of returning `download` for invalid input, but add an internal `try_sanitize_filename(input, byte_limit) -> Option<String>` so a rejected candidate falls through to the **next source** rather than silently winning as `download`. Process separators (`/`, `\`) in header text as untrusted path text, take the last nonempty component, reject empty/`.`/`..`/all-dots, remove controls/NUL, replace `< > : " | ? *` per character (do not strip everything before `:`), trim Windows-invalid trailing spaces/periods, and prefix reserved Windows device basenames case-insensitively, including `COM¹`–`COM³` and `LPT¹`–`LPT³` with or without extensions. Apply the portable Windows/Unix invalid-character union regardless of build target. Truncate on UTF-8 boundaries, preserving an extension when possible, and re-check reserved/empty/normal-component invariants **after** truncation. For URL basenames, **reject** a percent-decoded `/` or `\` (rather than re-splitting it and promoting a substring); try the next source. Every accepted name must be exactly one normal component under the caller directory.

For directory requests, the final basename and every generated ` (n)` sibling must fit the configured UTF-8 byte cap and the 250-byte effective cap, including `.part` headroom. Reserve suffix bytes **before** extension-preserving truncation, so suffixes never collide by truncating away their distinguishing number. Construct only `directory.join(single_normal_component)`. This is a **lexical** containment invariant; a trusted directory or symlinked directory can have a different canonical path. Explicit-file input is never sanitized or truncated in existing modes. For explicit-file `Rename`, keep the original base name verbatim if it is free; generated siblings must obey the `.part` headroom or fail with `DestinationConflict` if a unique safe sibling cannot be represented.

## Ordering, resume and collision policy

Existing explicit-file policies remain: `FailIfExists` pre-check → `DestinationLease::acquire` → checkpoint identity/resolver/`begin_admission` → probe → finalize admission → transfer → atomic publish. For directory mode: validate request/directory (no artifact) → probe once (with current auth/retry/cancel/origin rules) → resolve name → select candidate/lease → derive `job_identity(original_url, final_destination)` and `CheckpointResolveContext` → `begin_admission` and finalize with already obtained probe validators → transfer/verify/publish. For explicit-file `Rename`, select candidate/lease and begin admission before probing, preserving pre-network admission; finalize after probe. Route each mode through shared downstream execution; the job never reprobes merely because its destination was selected late.

Use one `#[non_exhaustive] OverwritePolicy` with new `Rename`; do not add a second collision policy. `FailIfExists` in directory mode checks the resolved destination after the probe and still publishes atomically with `PublishMode::NoReplace`; `Replace` and `ResumeIfMatching` keep their existing mapping and checkpoint behavior at the resolved path. `Rename` always publishes using `NoReplace`, never `Replace`.

For `Rename`, generate basename, `stem (1).ext`, `stem (2).ext`, … through **stem (999).ext** (1,000 candidates including the base). Both target forms use the same selection algorithm:

- First, if `resume != Never`, search candidate partial siblings in numeric order for resumable state **before** taking a fresh free name. Under each candidate's `DestinationLease`, skip published finals and lease conflicts, derive its own checkpoint context/identity and use a crate-private `resume::flow` discovery variant of `begin_admission` that returns `None` for an absent checkpoint **even for `Required`**, without parsing an error string. Reuse the same store/resume validation and corrupt-state policy: fatal failures remain `Checkpoint`; only absence means continue scanning. Retain the selected store, lease and pending admission for finalization, never loading/admitting it twice. A structurally admitted checkpoint takes priority even over a free lower-numbered filename. Validator mismatch at final admission follows existing resume policy rather than changing the chosen filename. A stale `.part` with no usable checkpoint is never opened/truncated as a fresh transfer.
- Otherwise, choose the first candidate whose final entry and `.part` sibling are absent, acquire its lease nonblocking (skip only `DestinationConflict`; propagate permissions/other lease errors), re-check both entries **under the lease**, and hold that lease through checkpoint/partial/commit/cleanup. Use `symlink_metadata` (not `Path::exists`) to treat dangling symlinks and other non-regular entries as occupied. A conflicting contender tries the next name. Existing `.part` under a name is skipped, never overwritten. If every candidate is occupied/unavailable, fail `DestinationConflict`; if `ResumePolicy::Required` has no usable checkpoint, preserve the existing `Checkpoint` failure even when no free candidate exists.
- Do not reserve a suffix merely on an unlocked `exists()` check. Selection can race with non-cooperating directory writers; atomic no-replace at publication is the final protection and may fail with `DestinationConflict` without clobbering anyone. The chosen name, identity and event never change after transfer starts. Existing lockfiles are persistent and are created *during* acquisition; no `.part`, checkpoint or final output is created before a lease is held.

Default sidecars remain in `CheckpointResolveContext::destination_parent()`; custom stores use the same resolver contract. A retry of URL+directory resumes only when it resolves the same name (or discovers a checkpointed `Rename` sibling). If server metadata changes its name, that yields a different identity and a fresh job. `ResumePolicy::Required` with no checkpoint is `Checkpoint` (directory mode may already have probed). Document any bounded scan cost/extra lockfiles for `Rename` and avoid creating lockfiles for obviously absent resumable candidates.

## Errors, documentation and security

No new `DestinationNaming` error/category: an always-valid fallback makes that path unreachable. Invalid directory/options use `Configuration` where determinable before networking; parent/lease failures use the existing `Commit`/`PermissionDenied`; exhaustion and final-name races use `DestinationConflict`; missing required state uses `Checkpoint`. Keep existing URL redaction at logging boundaries. A filename can itself originate from a sensitive URL path or header: do **not** claim paths are inherently non-secret; paths remain visible via resolved/committed events, the accessor, terminal output and filesystem entries, and must not be duplicated into raw-header/URL logs.

Update `docs/api-surface.md`, `docs/api-compatibility.md`, `CHANGELOG.md` and the API surface inventory script for all additive root re-exports/methods/variants. Extend the external-consumer fixture to compile an unchanged literal `DownloadRequest` plus the new directory API. Preserve `io`, `job`, `http::probe` and `resume` module visibility boundaries. Add an OpenSpec change under `openspec/changes/<change-id>/` covering consumer API, HTTP transport, security, resume/storage, observability and download outcomes; its delta should explicitly distinguish directory post-probe admission from file pre-probe admission.

## Acceptance and verification

- Parser tests: `filename*` wins when valid, falls back to `filename` when malformed or rejected by sanitization, handles semicolons/escapes in quoted strings, raw non-UTF-8 ordinary filename, duplicate parameters/headers, unsupported charset, and hostile long input.
- Resolution tests: redirect HEAD final URL vs original, no intermediate/GET/transfer-response renaming; trailing `/`, query/fragment exclusion, malformed percent escape fallthrough, single percent-decode, invalid UTF-8 replacement, encoded separator rejection, source fallthrough and fallback; portable sanitizer (including superscript Windows device names) and traversal/normal-component property.
- Storage tests: 250-byte default `.part` headroom, configured cap and invalid option rejection, multibyte and suffix/extension truncation; pre-lease artifact guarantee, no replacement under `Rename`, collision/1,000-candidate exhaustion/stale-part and dangling-symlink handling, process-local and cross-process contention, two concurrent identical requests, checkpoint-first renamed retries, Required without checkpoint, different server name ⇒ different identity, custom checkpoint resolver receives the final path.
- Behavior tests: directory mode probes once (HEAD and optional validating ranged GET consume no body) before lease/admission; original `File` modes still reject existing output or Required-without-checkpoint **before** network, retain prior event sequences, use the same transfer/commit path; `File + Rename` selects before network; new event/accessor precede progress and agree with terminal path. Cancellation/deadline during pre-lease probe creates no partial/checkpoint.
- For the future implementation, extend `crates/engine/src/fuzz_targets.rs::fuzz_content_disposition` and its corpus smoke test with URL resolution + name containment cases. Verify `cargo fmt --all -- --check`, `scripts/api_surface_check.sh`, `cargo test --workspace --all-targets --locked`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, targeted filesystem/resume/event tests, `scripts/ci_lane.sh all` (writes evidence), and `openspec validate <change-id> --strict` after creating the change. Run macOS/Windows filesystem tests in CI; lexical safety on one OS alone does not prove portable publication. None of these commands run for this markdown-only review.
