# KDown Engine — system analysis

**Reviewed revision:** `1cf85ac5864cc2c2e0c310580dd9042f31bfcd76` (2026-09-27 UTC). **Scope:** the Rust workspace, engine implementation, tests, release tooling, and documentation. This is a source review plus bounded, offline, isolated-loopback reproductions with dummy URLs/credentials and scratch files; it is **not** a complete audit of every state-machine interleaving or platform. The findings below are recommendations, not implemented fixes.

## Executive assessment

KDown is an unusually ambitious, well-instrumented *library* downloader. Its design has real strengths: typed terminal outcomes, range-response validation before writes, resumable checkpoints, RAII-style write/lease ownership, bounded per-job pipeline accounting, origin coordination, and broad test/benchmark/release infrastructure. However, **do not declare it production-stable yet**. Local reproductions establish cross-origin credential disclosure, incorrect successful outputs, reuse of unverified checkpoint data, and writes through attacker-placed partial-file symlinks. There are also demonstrable contract gaps around durable checkpoints, segmented authorization, deadlines, metrics, and release evidence. The existing performance report explicitly says stability is not declared (`docs/performance-report-v1.md`).

Priority is **P0: stop incorrect publication and trust-boundary violations**, **P1: restore advertised controls/durability**, then **P2: improve diagnostics, verification, and maintainability**. Here, P0/P1/P2 are remediation priorities, not CVSS scores. A security consequence requires the stated trust preconditions; the library cannot protect against an attacker who already controls the host application or all its files.

## Architecture and intended behavior

`DownloadController` (`crates/engine/src/job/controller.rs`) starts a Tokio task per download and returns a live `DownloadHandle` plus a join handle. Its flow is destination lease → checkpoint-store resolution/admission → HEAD/range probe → sequential or segmented transfer → size/optional hash verification → temporary-output publication → checkpoint cleanup. The production `HttpTransport` (`http/transport.rs`) wraps Hyper/Rustls; `http/execution.rs` mediates semantic probe/transfer results, while `http/range.rs` and `http/validators.rs` validate ranges and resource identity. Segmented workers and interval/lease scheduling live in `job/segmented.rs` and `scheduler/`. `io/` owns positional writes, memory reservations, write lanes, output-session lifecycle, destination locking, and filesystem publication. `resume/` owns checkpoint formats, admission, and sidecar storage. `metrics/` and `control/` provide runtime counters, events, rate limiting, cancellation, and origin coordination. The repo is a single-crate Cargo workspace with a substantial internal and external test matrix, fuzz harness, scripted/fixture servers, and release-evidence tooling.

### What's good

- **Clear successful outcome:** `Result<CompletedDownload, DownloadRunError>` means a normal transfer failure is not `Ok`; transfer, infrastructure, and cancellation have separate typed outcomes and partial accounting (`error.rs`, `controller.rs`).
- **Thoughtful transfer boundaries:** the HTTP adapter interprets statuses/ranges before passing body data; segmented leases use generation fencing and positional, write-only capabilities (`http/execution.rs`, `http/range.rs`, `scheduler/core.rs`, `io/output_session.rs`). A changing or malformed ranged response has a path to fail before publishing.
- **Non-destructive final publication:** default no-replace uses an atomic hard link; replace uses a same-directory rename, with an explicit no-clobber race test (`io/publish.rs`). The per-destination lease combines process-local and OS file locks (`io/destination_lease.rs`). These are sound ideas **when the temp file really belongs to the job**; see P0 below.
- **Resource-aware design:** `io/transfer_ledger.rs` charges frames/writes/checkpoints per job and aggregate; `http/transport.rs` configures bounded H1/H2 ingress and reserves connection footprints. Limitations of RSS/kernel memory are explicitly documented rather than hidden. Sequential and segmented paths have test coverage.
- **Verification breadth and honesty:** property, fuzz, crash/restart, sink-fault, H1/H2, proxy, TLS, filesystem, and consumer-API tests exist. CI covers Linux/macOS/Windows and MSRV; the benchmark gate separates throughput, CPU, amplification, memory and noise. The performance report states the loopback baseline and missing platform/dynamic-check evidence are blockers rather than calling a noisy measurement a pass.
- **Intentional API boundary:** implementation modules are private, with a root facade, migration policy and consumer compile tests (`lib.rs`, `docs/api-surface.md`, `docs/migration-0.1.md`).

## Required changes — validated findings

### P0 — Cross-origin redirects forward credentials by default

**Boundary/outcome:** a server controlling a redirect can point an authorized request at a different HTTP origin. The engine then sends the caller's `Authorization` and `Cookie` headers to that origin even though `forward_credentials_cross_origin` defaults to `false`. Two isolated servers, a redirect and dummy credentials reproduced both headers at the second server (HEAD and GET). This is actual disclosure of the caller's credentials to the redirect target, not merely a missing best practice.

**Cause:** `http/transport.rs:499-504` passes **response** headers to `RedirectTracker::decide` as `current_headers`; `http/redirect.rs:138-143` sets `strip_credentials` only if those headers contain authorization/cookie. Ordinary 302 response headers do not. `http/transport.rs:521-524,570` therefore forwards request credentials. There is also an origin-comparison correctness concern: `origin_of` in `http/redirect.rs:154` uses string splitting on an unresolved `Location`, not normalized resolved URL/authority.

**Fix/test:** resolve each Location first; compare parsed **current request** and target origins; when crossing origins, clear sensitive request headers (including proxy-authorization and explicitly credential-marked headers as applicable) *before dispatch*, irrespective of the response's headers. Keep stripping latched over later hops. Add two-listener tests for absolute and relative redirects, default and explicit opt-in, multiple hops, cookies, and authorization-provider headers. This is the top security fix.

### P0 — A successful download can contain bytes never received from the server

**Outcome A, known length:** HEAD reports six bytes but GET sends a valid three-byte response. With default `preallocate_output=true`, the job returned success and published `new\0\0\0` (completed counter: 3). **Outcome B, unknown length:** put `STALE-TAIL` in `<destination>.part`, serve an unknown-length, chunked `new`; the job returned success and published `newLE-TAIL`. Both ran with the real controller and local servers. No requested digest was supplied; with a trustworthy expected digest the hash check would catch these particular cases. Without one, `Ok` does **not** currently imply that every published byte was received and verified.

**Cause:** `io/sink.rs:177-199` opens an existing `.part` with `create(true), truncate(false)` even for a fresh run. `OutputSession::create` (`io/output_session.rs:171-191`) uses this path. `io/sink.rs:355-359` sets the file length when known; `controller.rs:2212-2240` verifies *filesystem length*, not the number of uniquely acknowledged payload bytes; no-digest jobs skip `verify_hashes` (`controller.rs:2250-2267`). With unknown size there is no final-size check (`controller.rs:2038,2230`).

**Fix/test:** fresh output must be a newly owned, regular inode and never inherit stale bytes; either atomically create a unique temp name or securely replace/truncate only after validating ownership and cleanup semantics. For a known length require exact received/accepted coverage of `[0,total)` (accounting for checkpoint-reused ranges) before commit, not just `metadata.len()`. For unknown length explicitly finalize/truncate to the acknowledged EOF and reject incompatible partial state. Reproduce both cases with real H1/H2 adapters, also after abort/retry and with sparse preallocation.

### P0 — Reused checkpoint bytes can bypass resource identity verification

**Outcome:** a locally saved checkpoint said the six-byte `.part` was fully complete (`OLDOLD`); a new HEAD for the same URL reported six bytes of a different body (`NEWNEW`) with **no validators**. Admission accepted the checkpoint and the controller published `OLDOLD` **without issuing a GET**. The simulated checkpoint had an old ETag, but the new response omitted it. Both HTTP responses and files were dummy fixtures. A trusted SHA-256 expectation would mitigate a bad final body; by default there is none.

**Cause:** `resume/flow.rs:297` calls `same_generation`, but `http/validators.rs:50-69` only compares fields *when both sides supply them*. Absence of a previously required strong validator therefore counts as a match; `ResourceValidators::resume_capable()` (`validators.rs:36`) exists but is not used on the admission path. `resume/flow.rs:339-356` checks only local `.part` length, not byte integrity or file identity; fully covered checkpoints take the no-fetch fast path (`controller.rs:1258-1262`). Size equality is not generation identity.

**Fix/test:** treat missing/noncomparable strong validators as **insufficient evidence to reuse**, and reject or restart from zero according to policy before trusting ranges. Require a stable validator on both saved and current representations, including correct weak-ETag handling; if validator continuity cannot be established, re-download. Bind checkpoint to the actual temp inode/identity or verify persisted chunk digests when local tampering must be resisted. Add explicit ETag-disappears, no-validator, Last-Modified-changes, and fully-complete-checkpoint cases. Do not confuse a metadata-only `HEAD` with proof of unchanged bytes.

### P0 — Pre-existing `.part` symlink redirects writes outside the job's output

**Boundary/outcome:** if another local actor can create/replace entries in the destination directory, placing a symlink at `<destination>.part` allows engine writes to affect its target. In an isolated fixture, a symlink from `symlink.part` to an unrelated dummy file caused that file's contents to change from `UNCHANGED` to `new` while the download reported success. The final publication is a hard link/rename of the path entry, not proof that the write handle referenced that entry's own regular inode. The impact is limited by the engine process's filesystem privileges and requires an attacker-writable directory; it is **not** a remote-only exploit or protection against a host application intentionally using such a directory.

**Cause:** `io/sink.rs:177-203` follows existing symlinks on open; `io/publish.rs:99-137` publishes by pathname. `DestinationLease` locks a sibling lockfile for cooperative KDown jobs, but it does not exclude non-cooperating local writers or protect against replacement of the temp path. The sidecar path likewise deserves the same boundary review (`resume/checkpoint_store.rs:216-266`).

**Fix/test:** for a fresh temp use exclusive, no-follow creation of a unique regular file; for resume open with no-follow and validate inode/file identity against checkpoint state. Prefer directory-relative, no-follow operations and retain a verified binding from write handle to published inode; handle hostile directory-entry replacement and hard links, not just symlinks. Document a trusted-directory requirement if full defense is intentionally out of scope. Add symlink and rename-race fixtures with unrelated dummy files; never run tests against real sensitive paths.

### P1 — Durable sequential checkpoints are persisted before data fsync

`DurabilityMode::Durable` is documented as syncing output data before checkpoint ranges (`README.md`, `resume/durable_ranges.rs`). Segmented saves explicitly call `sync_data()` **before** `save_atomic()` (`job/segmented.rs:2868-2923`). In the sequential path, `controller.rs:1760-1805,1810-1836` advances the tracker with `page_cache_ack` and saves ranges with `save_checkpoint_bounded`; no preceding output-file sync appears on that path. The `DurableRangeTracker` uses the same page-cache advancement in both modes (`resume/durable_ranges.rs:44-70`), while `FileCheckpointStore` only fsyncs the checkpoint file and directory (`resume/checkpoint_store.rs:241-266`). **Source-established contract violation:** after sudden power loss, metadata can claim completed bytes not flushed to disk. This specific power-loss outcome was not injected in this review.

**Fix/test:** use a shared mode-aware checkpoint-save routine in both modes, sync the output data before admitting the corresponding frontier in Durable mode, then persist/dir-sync the checkpoint. Add ordered fault-injection tests for sync failure, save failure, pause and crash restart in sequential and segmented modes. Performance mode should retain its documented weaker guarantee.

### P1 — Segmented workers omit the request's convenience Authorization header

`controller.rs:825-834` adds `DownloadRequest.authorization` to the probe's headers, but `job/segmented.rs:923-927` creates worker specs from `request.headers` alone. With a local server requiring a dummy bearer token on *every* GET, the HEAD/range probe succeeded, but the segmented worker sent a GET without the token and the job failed `AuthenticationRequired`. Thus a request may work in sequential mode and fail only when segmentation becomes eligible. Provider/challenge handling in segmented workers should be reviewed too; no worker-side use of `credential_provider` appears in `job/segmented.rs`.

**Fix/test:** derive an authenticated, redirect-sanitized transfer request context from the probe rather than reconstructing it from only one field. Ensure the final-origin redirect policy never re-attaches stripped credentials. Test bearer and challenge-provider credentials under sequential/segmented H1/H2 and cross-origin redirects.

### P1 — Advertised `job_deadline` is not enforced; cancellation sleeps are not prompt

`TransferPolicy.job_deadline` is defined at `config.rs:210` but has no consumer in `controller.rs` or `segmented.rs`; a local 10 ms deadline allowed a 207 ms transfer to complete successfully. Probe, sequential and segmented retry branches use plain `tokio::time::sleep(delay)` (`controller.rs:951,1497,1992`; `segmented.rs:1588`). Cancelling during a one-second server-directed backoff took about 944 ms to return (and would take longer for a larger permitted delay). Pending HTTP header waits also need cancellation review; a cancel check only before dispatch is not sufficient for a blocked request.

**Fix/test:** wire a single monotonic job deadline through probe, admission, body, retries, hashing and commit, with clear semantics for interruption of already-started publication. Use cancellation-aware selects for retry/header waits, and bounded tests measuring cancellation and deadline latency under 503/Retry-After, stalled headers and paused workers. Keep cleanup and typed terminal outcomes intact.

### P1 — Checkpoint-size budget estimate omits untrusted validator lengths

`Checkpoint::serialized_size_estimate()` (`resume/checkpoint.rs:101-113`) counts URLs/ranges/digests but does not count `validators.etag` or `validators.last_modified`. A dummy ETag of 8,192 bytes produced an estimate of **561** vs **8,508** serialized bytes; `check_serialized_within(1024)` accepted it. The default file store has a second actual-size check *after* serialization (`resume/checkpoint_store.rs:218-230`), which prevents an oversized default sidecar write but not the promised **pre-allocation** guarantee or an unchecked injected store. The in-memory ledger similarly reserves the underestimated size (`controller.rs:2397-2415`; `segmented.rs:2902-2922`). Remote response/header limits cap this input in the default transport; the concrete consequence here is a broken configurable memory/checkpoint bound, not unbounded demonstrated OOM.

**Fix/test:** include escaped validator strings and all serialized fields in a checked upper bound, or use a bounded streaming serializer with correct reservation. Test large validator values, escaping, capped stores and the injected resolver path; assert recorded peak never understates held bytes.

## Additional bad / operational risks

1. **Metrics misstate received bytes.** `TransferAccounting.wire_amplification()` (`error.rs:358-365`) adds `wasted_bytes` to `bytes_downloaded_from_network` despite both sequential and segmented counters recording network bytes when read and later marking already received bytes as wasted (`controller.rs:1758-1759,1903-1909`; `segmented.rs:1911-1921`). Dummy counters network=150, completed=100, wasted=50 return **2.0** rather than **1.5**. Use `network_bytes / unique_completed_bytes`, document reused-byte denominator, and test a real retry in both transfer modes. This is an observability flaw; the benchmark's server-emitted-byte amplification is a separate axis.
2. **Sensitive URLs in debug/error/checkpoint paths.** `DownloadRequest` and `RequestSpec` intentionally hide header values but include raw `.url` in `Debug` (`controller.rs:72-78`; `http/transport.rs:132-141`). A dummy URL with userinfo and `token=` printed both verbatim. `http/transport.rs:382-385` incorporates raw URLs in parse errors; `resume/checkpoint.rs:41-47` stores `original_url`/`final_url` in sidecar JSON, including signed query strings if present. `Redactor::new()` only strips userinfo by default; query secrets require opt-in marking (`redact.rs:11,56-104`). Any host logger that formats a request/error, or lower-trust reader of a sidecar in a shared directory, can receive secrets. Make default debug/error output origin/path-safe, redact known secret keys, provide a caller-configurable redaction policy and storage permissions; retain raw URLs only where absolutely necessary for requests, not diagnostics. Do not treat every caller URL as secret, but do not promise generic secret-safe diagnostics in their presence.
3. **Events do not terminate with the job.** `DownloadHandle` retains an `Arc<EventHub>` (`controller.rs:162-181`); a subscriber obtained from that handle can wait on `EventStream::next()` (`metrics/events.rs:235-241`) forever after `Completed`. An isolated completed job left the stream open after events were drained. Document this and provide a guaranteed final event or a close/finished-aware stream API; `snapshot()` and job task are currently the only robust terminal checks.
4. **Release gate has avoidable fail-open options.** In `scripts/release_gate.py:151-166`, a non-approving smoke gate is marked satisfied before its timestamp and commit are checked. A synthetic manifest with a passing 26-year-old smoke fragment from the wrong commit was reported stable. `evaluate(..., commit=None)` also skips revision binding (`release_gate.py:174`). Release CI passes `--commit`, but the public `check` CLI does not require it. Validate freshness/commit for *every* required gate, including non-approving prerequisites; require a revision for production-stability checks and extend self-tests. A gate cannot authenticate manually fabricated JSON; provenance of uploaded fragments remains a process responsibility.
5. **`max_active_jobs` does not limit jobs.** Defined/defaulted in `config.rs:632,701` and validated at `config.rs:887`, but there is no admission use in `controller.rs`; `start()` spawns unconditionally (`controller.rs:550-663`). Memory/connection caps still provide some backpressure, but unbounded per-job task, handles, state and filesystem effects remain possible if a host starts many jobs. Implement an RAII admission permit or rename/document the option as non-operative until implemented.
6. **Complexity and test ergonomics.** `job/segmented.rs` is ~4,100 lines, `job/controller.rs` ~3,000, the benchmark harness ~3,900, with large configuration and scripting surfaces. This increases review cost and the odds of sequential/segmented policy drift (visible in authorization and durability). Centralize shared decisions (credential/redirect context, checkpoint durability, final coverage) before further performance tuning. Static API inventory checks inspect the root and a compile fixture, not a full public-signature diff (`scripts/api_surface_check.sh`). `lib.rs` points at `KDownSpec.md`, which is absent from tracked repository files; fix or remove broken references. Workspace lints are defined in root `Cargo.toml` but the member `crates/engine/Cargo.toml` does not opt into `[lints] workspace = true`; enable that after assessing warnings.
7. **Performance conclusions have limits.** `docs/performance-report-v1.md` records shaped 10 ms/100 Mbps and 80 ms/20 Mbps suites on a pinned development host, but loopback evidence is explicitly too noisy. The managed-memory high-water is engine-accounted pipeline memory, not total process RSS. Do not infer production throughput across hardware/filesystems or release safety from these micro/synthetic profiles alone. Re-run on matched controlled hardware and monitor production-like RSS, disk I/O, concurrency, and tail latency.

## Verification status and limits

- A sandboxed, offline, two-loopback-server harness using real `HttpTransport` reproduced the redirect, known-/unknown-length publication, missing-validator resume, segmented authorization, ignored 10 ms deadline, ~944 ms cancellation backoff, `.part` symlink overwrite, URL debug output, checkpoint estimate and amplification counterexamples above. An isolated release-gate evaluation reproduced the stale-smoke and missing-commit cases. All payloads, files, and credentials were dummy/scratch-only; no external endpoints were contacted.
- In a separately isolated targeted run, `release_gate.py self-test` and `bench_gate.py self-test` passed; external consumer fixture **3/3**, validators **7/7**, publication **9/9**, and doctest **1/1** passed. Passing tests do not negate the counterexamples: several current tests model only same-origin redirects, assert size using preallocated file metadata, or use matching validators.
- A full workspace suite was **not completed** in this review. Initial attempts lacked sandbox-visible CA roots/corpus and then hit scratch test-resource limits; those are harness limitations, not claims that the repository's normal CI fails. I did not rerun macOS/Windows, fuzz, Miri, sanitizers, cargo-audit, or release benchmarks. Historical results in `docs/performance-report-v1.md` are reported as historical, not independent verification of this commit.
- Platform-specific atomic rename/dir-sync semantics, shared-directory attack prerequisites, external consumers' secret-URL practices, and deployment access controls require owner validation. The security findings above distinguish observed dummy impact from those assumptions; no claim of arbitrary remote file access or crash/power-loss reproduction is made.

## Recommended remediation sequence

1. **Immediately:** fix redirect credential stripping; block publication from stale/preallocated holes; require strong comparable validators before checkpoint reuse; eliminate symlink-following/path-to-handle races on `.part`. Add minimal end-to-end regression tests for each before releasing.
2. **Next:** share the authenticated transfer context across probe/sequential/segmented; fix Durable mode ordering in the sequential path; enforce deadline and cancellation across waits; repair the checkpoint-size estimate and make `max_active_jobs` real.
3. **Then:** fix amplification math, secret-safe diagnostics and event termination; make all release-evidence prerequisites fresh and commit-bound; unify policy codepaths and strengthen API checks.
4. **Before claiming stability:** run the full locked suite and failure/crash matrix on all supported platforms; rerun the fuzz, dynamic checks, dependency audit, and controlled loopback performance gate with evidence for the exact candidate commit. Revisit documented advisory exceptions and only declare production-stable when the mandatory release gate passes **and** these correctness/security issues are resolved.
